---Updated Flow For Flats---

1. Initial State: 
   System starts with NO flats and NO users attached to flats.

2. User Signup (Unassigned Pool): 
   Owners and Residents register in the app (Google/Email). They are placed in the `users` table, but their `flat_id` is NULL. They wait for Admin assignment.

3. Create Flat: 
   Admin creates a new flat and selects 1 Owner and 0-to-N Residents from the unassigned pool.
   - DB Action: Insert into `flats`.
   - DB Action: Update selected users with the new `flat_id`.
   - DB Action: Automatically generate the 1st `billing_record` for the flat.
   - **NOTIFICATION TRIGGER**: Send welcome notification/reminder to new Owner/Residents via OneSignal (real-time/push).

4. Add/Remove Residents (Update Flat):
   - Adding: Admin selects user from unassigned pool -> backend uses `array_append(resident_ids, new_id)` -> sets user's `flat_id = flat_uuid`.
   - Removing (Eviction): Admin removes a tenant -> backend uses `array_remove(resident_ids, old_id)` -> sets user's `flat_id = NULL` (they return to the unassigned pool).

5. Change Owner (Update Flat):
   - Admin reassigns the flat to a new Owner.
   - DB Action: Old Owner's `flat_id` is set to NULL (they go back to the unassigned pool. DO NOT set their `is_active = FALSE`).
   - DB Action: New Owner's `flat_id` is updated. 
   - DB Action: `flats.owner_id` is updated to the new Owner.

6. Delete Flat (Soft Deletion):
   - Admin deletes a flat (e.g., if created by mistake or building restructure).
   - DB Action: `flats.is_active` is set to FALSE.
   - DB Action: `flats.owner_id = NULL` and `flats.resident_ids = {}`.
   - DB Action: All associated users have their `flat_id = NULL` so they can be assigned elsewhere.
   - Past billing records stay perfectly intact for financial history!
