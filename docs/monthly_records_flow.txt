---Updated Flow For Monthly Records---

SECTION 1: FETCHING RECORDS (GET REQUEST)

1. Case 1: Initial State (No Records)
   - Scenario: The society is brand new, no flats exist, or no bills have been generated for the selected month.
   - DB Condition: No matching rows in the database for the given month/year.
   - UI Behavior: Display a friendly "No records found for this period" message.

2. Case 2: Data Present (Dynamic Time Filtering)
   The Admin UI contains dynamic dropdowns/filters for Month and Year. 
   A single dynamic SQL backend query handles all the following sub-cases:
   
   - Subcase A (Default View): Current Month & Current Year are auto-selected. Shows active pending/paid dues.
   - Subcase B (Future Months): Since bills aren't generated until the month starts, the UI should either disable future months in the dropdown, or safely display "No records generated yet".
   - Subcase C (Past Months / Previous Years): Admin selects older dates. The query dynamically filters and returns historical data.
   - Subcase D (All Data): Admin selects "All". The query ignores date filters and returns the entire history.

SECTION 2: ADMIN "MARK AS PAID" ACTIONS (POST REQUEST)

The Admin wants to change a flat's status from "Pending" to "Paid" on the Monthly Records page. Strict validation must be enforced to ensure financial tracking.

1. Scenario A: Admin attempts to mark "Paid" BUT NO payment record exists.
   - Action: Admin clicks the "Mark as Paid" button.
   - Backend Validation: Database checks if an actual transaction exists in the `payments` table for this specific month/flat.
   - Result: Verification fails (Transaction missing).
   - UI Behavior: 
     * Action is BLOCKED. 
     * Shows Warning: "No payment record found. Cannot mark as paid."
     * Shows an Action Button: "Go to Payment Entry".
     * Redirect: Navigates Admin to the Payment Entry page, passing context via URL Search Params (e.g., `/payment-entry?flatId=XYZ&month=3&year=2026`).

2. Scenario B: The Payment Entry Component (Navigated from Warning)
   - Action: Admin arrives at the Payment Entry page.
   - UI Behavior: The component reads the query params (`flatId`, `month`, `year`). If present, it automatically populates the search boxes/dropdowns to save time.
   - Admin Action: Fills out the mode (Cash/Cheque) and submits the manual payment entry. 
   - Consequence: A physical transaction is now logged in the database.

3. Scenario C: Admin marks "Paid" AND a payment record exists.
   - Condition: A payment log was just created manually (Scenario B) or was added previously.
   - Action: Admin clicks "Mark as Paid" on the Monthly Records page.
   - Backend Validation: Verifies the payment transaction exists.
   - Result: SUCCESS! The flat's subscription/bill status is officially updated to "Paid".
   - **NOTIFICATION TRIGGER**: Backend inserts into `notifications` table and calls OneSignal API to update the Resident's UI in real-time.
