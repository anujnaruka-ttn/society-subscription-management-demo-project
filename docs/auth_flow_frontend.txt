# Frontend and Backend Authentication Flow (NextAuth + Express)

This document explains how your frontend (Next.js with NextAuth) communicates with your custom Express backend (`auth.ts` middleware) for Google authentication and standard authentication.

## 1. Do we still need `loginGoogle` and `auth0_id`? 
**YES! Absolutely.**
- `auth0_id` is how your database recognizes that a specific Resident is linked to a Google Account.
- `loginGoogle` is the API route your frontend calls to convert a Google Login into your Custom Backend JWT.

## 2. The Complete Login Flow (Step-by-Step)
Here is what happens when a user clicks "Login with Google":

1. **Frontend (NextAuth):** User clicks "Sign in with Google". Google authenticates them and sends their Profile (`email`, `name`, and `providerAccountId` which NextAuth gets).
2. **Frontend `signIn` / `jwt` Callback:** NextAuth catches this response. Inside your NextAuth configuration (`[...nextauth].ts` or `route.ts`), you immediately make an HTTP POST request to your backend's `/api/auth/google/login` containing:
   - `email`: profile.email
   - `name`: profile.name
   - `auth0_id`: account.providerAccountId
3. **Backend (`loginGoogle`):**
   - The backend checks if the user exists using `email`.
   - If they don't exist, it creates a new Resident.
   - It updates the `auth0_id` in the database just in case.
   - It **generates your custom JWT Token** using the `generateToken` utility.
   - It sends the `token` back to the frontend in the JSON response.
4. **Frontend `jwt` / `session` Callback:** NextAuth takes the `token` sent by your backend and saves it inside the NextAuth Session Cookie.
   - The user is now officially logged into the Next.js app!

## 3. How Authenticated API Requests Work
Whenever your frontend makes a request to a protected route on your backend (like fetching billing details):
1. **Frontend:** Reads the custom `token` from the NextAuth session.
2. **Frontend:** Attaches it to the request header as `Authorization: Bearer <token>`.
3. **Backend (`auth.ts` Middleware):** Reads the Bearer token, verifies it using `jwt.verify(token, ENV.JWT_SECRET)`, and sets `req.user`.
4. **Backend:** If the token is valid, the request proceeds automatically!

## 4. The Complete Logout Flow
Here is what happens when a user clicks "Logout":

1. **Frontend (User Action):** User clicks the "Logout" button.
2. **Frontend (NextAuth):** You call the `signOut()` function provided by NextAuth.
3. **Frontend (NextAuth Action):** NextAuth **deletes its session cookie** from the user's browser automatically.
4. **Backend:** *Nothing happens! You do not need to call the Express server.*
   - Why? Because NextAuth handles standard JWTs completely statelessly. The token is stored purely on the client's browser. If you delete the cookie on the browser, the user no longer has their token securely saved. 
   - The next time they try to fetch `/api/billing`, they won't have a token to send, and your `auth.ts` middleware will perfectly block them.

### Summary
- You do NOT call the backend to Log Out. Calling `signOut()` on NextAuth seamlessly handles it. 
- You still need `loginGoogle` to generate your tokens and insert new users!
